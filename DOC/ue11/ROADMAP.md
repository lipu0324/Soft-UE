# Soft-UE 扩充为 UE 1.1 全栈软件仿真的实施计划

## 1. 目标与技术基线

保留 Soft-UE 自研 SES/PDS 内核，将其扩充为**可重复运行、可注入故障、可观测协议状态的软件行为仿真平台**。

最终覆盖：

- **主机侧**：原生异步 API、libfabric 映射、SES、PDS、CMS、TSS。
- **网络侧**：多端点、交换机、队列、路由、多路径、拥塞反馈和故障模型。
- **链路侧**：LLR、CBFC/PFC、能力协商等行为模型。
- **物理层抽象**：链路速率、传播延迟、误码、FEC 延迟与统计，不进行电气或 RTL 逐周期仿真。
- **管理侧**：能力发现、JobID、内存权限、安全域、拓扑配置和统计。
- **Profile**：依次完成 AI Base、AI Full/HPC、Unified Local。

第一版面向 **2～64 个端点**。第一个正式验收目标是 **AI Base 在最佳努力网络中的端到端正确性**。

技术依据固定为：

| 来源 | 使用方式 |
|---|---|
| [UE Specification 1.1](/workspace/attachments/e08a9b60-7d8e-468b-884f-041c53b800c2/UE-Specification-1.1.pdf) | 规范依据，以 §3.3 的 Profile 矩阵及各层规范要求建立验收项 |
| [Soft-UE](https://github.com/lipu0324/Soft-UE/tree/4a4e6d874909720097b1ae20302a538a97116976) | 自研实现基线，提交 `4a4e6d874909` |
| [uet-ref-prov](/workspace/uet-ref-prov/README.md) | 差分测试、报文互通和选择性复用，提交 `5b4e0491329b` |

官方仓库是**部分实现参考**。其拥塞控制仍标注基于旧版规范，RODL 等 1.1 新功能也未完整覆盖；发生差异时，以 UE 1.1 规范为准。标准第 8 章沿用的旧 Profile 名称与 §3.3 不一致，纳入勘误记录，不据此缩减四种 Profile 的范围。

## 2. 架构与接口改造

### 统一协议内核，支持两种运行方式

采用 C++17，构建轻量离散事件引擎，复用并修正现有 SES、PDSManager、IPDC、TPDC 逻辑。

- **仿真模式**：单进程承载多个端点及交换机，使用虚拟时间，作为协议正确性和网络实验的默认模式。
- **实时模式**：同一协议内核连接非阻塞网络后端，用于 libfabric 应用及官方仓库互通。
- 协议内核不创建线程、不调用 `sleep`，不直接读取系统时钟；现有线程管理器降为实时运行适配层。
- 每个端点独立拥有协议上下文、队列、定时器和配置，消除影响多实例仿真的全局状态。

### 必须新增或调整的接口

| 接口 | 职责与约束 |
|---|---|
| `IClock`、`ITimerQueue` | 注入时间、注册与取消定时事件；仿真时间采用整数纳秒 |
| `IPacketPort` | 非阻塞发送、接收回调、背压和发送结果通知 |
| 原生 `Endpoint` API | 提交操作、注册/注销内存、查询能力、读取完成事件 |
| CMS 接口 | 发送准入、发送记账、ACK/NACK/拥塞信号处理、路径熵选择 |
| 场景运行器 | 加载拓扑与工作负载，执行至指定时间或完成条件，导出结果 |

事件按“时间戳、递增序号”稳定排序；随机数由场景种子控制。取消后的定时器、已关闭连接的迟到事件，必须通过对象代次检查失效。

### 数据与兼容策略

- **标准线格式独立实现**：按规范位宽和端序编码，不直接序列化 C++ 位域、结构体或内部枚举。
- 现有 `SUP1/SUE1` 编码保留为明确标识的 legacy 路径，不计入标准报文验收。
- 所有远端内存访问经过 MR、JobID、权限和边界检查，禁止直接解引用报文中的地址；替换当前模拟的 `rkey` 校验。
- 原生接口与 `softue` libfabric provider 共用内核，采用 libfabric 2.0 基线；首先支持手动 progress。
- Unified Local 通过原生接口验收，不强行套用 libfabric 映射。
- 引入 CMake/CTest，保留原 Make 命令作为入口；RDMA 依赖改为可选，普通仿真测试无需 RNIC。

## 3. 分阶段实施与退出条件

按以下顺序推进。每个阶段都要求新增规范映射、自动化测试和可复现示例，通过后再进入下一阶段。

| 阶段 | 实施内容 | 阶段退出条件 |
|---|---|---|
| **M0：建立需求与回归基线** | 梳理标准 MUST、条件要求及选定可选功能；为每项关联规范章节、实现状态、测试和证据。复核现有测试实际经过的协议路径，区分消息通道测试与完整 SES/PDS 测试。 | 原有测试形成可运行基线；占位逻辑、协议差距和官方实现差距有明确清单。 |
| **M1：可重复的仿真运行时** | 抽离线程和真实时间；改造 RTO、连接生命周期及管理器为事件驱动。提供单链路、双端点场景与结构化事件轨迹。 | 相同场景和种子重复运行，协议轨迹与结果一致；关闭连接后无残留有效定时器；多端点状态隔离。 |
| **M2：标准报文与基础 PDS** | 实现 Ethernet、IPv4/IPv6、原生 UET、UET-over-UDP、CRC32C；完成 RUD、ROD、UUD。补齐建连、ACK/NACK、重复消除、窗口、重传、Clear/Close、序号回绕和资源回收。 | 标准报文黄金样例通过；数据包及 ACK 丢失、乱序、重复等故障场景通过；双方共同支持的原生报文路径可与官方实现互通。 |
| **M3：AI Base 语义与应用接口** | 实现该 Profile 要求的 NO_OP、SEND、DATAGRAM SEND、WRITE/WRITE IMM、非取回原子操作；完成相对/绝对寻址、JobID、MR 权限、操作完成语义。接入原生 API 和 libfabric provider。 | 操作实际改变目标内存；非法访问被拒绝且内存保持不变；本地完成、远端完成和错误完成符合规范。 |
| **M4：网络模型与 NSCC** | 实现叶脊拓扑、出口队列、链路串行化、ECN、合规 trimming、丢包及路径选择。按 UE 1.1 实现并接入 NSCC，使拥塞准入实际约束发送；落实 RUD 与 ROD 的路径规则。 | 完成双端点、incast、多流竞争、路径不对称和暂时断链测试；通过 AI Base 适用的全部必选项，形成首个正式端到端版本。 |
| **M5：AI Full 与 HPC** | 增加 READ、精确/通配 tag、deferrable send、rendezvous、取回原子/CAS、所需优化头和 Sync Group。独立实现 RUDI 的发起端状态、逐包响应与幂等约束。补充 RCCC、TFC、CSIG 及其适用范围。 | 两种 Profile 分别通过能力矩阵；RUDI 重传不会产生非幂等副作用；拥塞窗口与接收信用正确记账；能力发现只公布已实现功能。 |
| **M6：TSS 全路径** | 以 OpenSSL EVP 作为密码算法底层，按规范实现安全域、KDF 模式、AES-GCM、SSI/计数器、AN 与密钥轮换、认证失败处理及安全建连。提供可调度的 SDME 行为模型。 | 官方适用测试向量和独立标准向量通过；所有 KDF 模式覆盖轮换与边界；认证失败、旧 epoch 和非法安全域不会交付数据；安全模式下故障恢复通过。 |
| **M7：链路、PHY 抽象与管理** | 实现 LLR、CBFC/PFC 行为、协商与状态转换；建立速率、误码、FEC 延迟/统计模型。统一配置端点能力、JobID、安全域、队列、路由与计数器。 | 链路重试与端到端重传可分别观察；信用不足时禁止发送，恢复后能继续；链路能力不匹配与失效有明确结果；延迟和容量模型通过解析校验。 |
| **M8：Unified Local 与最终整合** | 实现 RODL 双向上下文、累计确认、局部事务头、消息打包、直接内存寻址、UFH_16/UFH_32 及相应 TSS 路径。RODL 默认支持重传，另验证关闭重传时的规定错误行为。 | 四种 Profile 各自通过适用要求；RODL 不套用 NSCC/trimming 路径；完成 64 端点综合回归和功能覆盖报告。 |

**四种 Profile 完成后的独立增强顺序：**

1. UE verbs 接入，首先按 §2.3 验收 AI Base 映射。
2. INC：交换机规约、管理模型、保留 PDC 和失败处理。
3. PCM：可替换的拥塞策略执行接口及标准规定行为。

这些增强单独声明能力，不作为 M8 的退出门槛。内核驱动、VFIO/QEMU 和真实 GPU/NCCL 接入放在后续系统集成阶段。

## 4. 验收体系与交付物

### 协议与内存正确性

- 对每项声明支持的功能建立正向、负向和边界测试；适用的必选项必须全部有通过证据。
- 验证分片、消息大小边界、零长度合法性、序号回绕、连接复用、资源耗尽和迟到报文。
- 验证 JobID 隔离、无效/撤销 `rkey`、越界、错误访问权限、并发原子操作和完成事件。
- 按标准区分保证：可靠操作的应用完成不得重复；RUDI 允许重复执行幂等操作；UUD 不推断远端收到。
- 用稀疏内存和流式 payload 验证大消息边界，避免依赖一次性分配数 GB 连续内存。

### 网络与安全组合测试

- 分别注入数据包、ACK、NACK 和控制包的丢失、延迟、重复及损坏。
- 覆盖乱序、trimming、ECN、拥塞、断链与恢复，以及 TSS 与这些场景的组合。
- 对 RUD、ROD、RUDI、UUD、RODL 分别建立适用测试，禁止使用统一可靠性或拥塞逻辑掩盖模式差异。
- 仿真测试的可靠性由自身协议实现承担；现有 InfiniBand RC 路径只作为适配回归。

### 独立对照与实验输出

- 标准样例、独立解析器和官方实现差分三类证据结合使用，避免编码器与解码器共享错误。
- 官方差分仅覆盖双方共同支持的功能；偏差记录规范条目、原始报文和双方状态轨迹。
- 每次实验输出：配置、版本、种子、Profile/能力、事件轨迹、PCAP、完成结果和统计。
- 统计包括有效吞吐、流完成时间、队列长度、重传、ECN、trim、信用停顿与公平性；同时报告事件吞吐和内存消耗。

CI 分为无需特权的快速回归、夜间故障组合/大消息测试，以及使用 veth/raw socket 的互通测试。硬件 RDMA 测试保留为独立可选任务。

## 5. 默认约束与完成定义

- 默认使用离散事件仿真；实时后端用于应用接入和互通，其墙钟耗时不作为仿真网络性能。
- 场景采用 YAML，结果采用 JSON、结构化事件轨迹和 PCAP；运行前校验 MTU、能力及拓扑配置。
- 选择性复用官方代码或向量时保留版本与许可证来源，不将官方静态测试密钥和轮换脚本作为最终密钥管理实现。
- 管理层提供可编程行为模型；真实 Redfish、NETCONF 服务和物理电路不纳入本轮验收。
- 按里程碑与退出条件推进，不预设未经人员配置确认的日历工期。

**项目完成的判断标准是：每个端点、每种已声明 Profile，都能从应用操作经过协议、网络和链路模型得到符合标准的结果，并能通过可重放证据解释成功、恢复或失败的原因。**
